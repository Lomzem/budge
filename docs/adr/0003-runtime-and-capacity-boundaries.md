# Runtime and capacity boundaries

Each deployment holds one owner's budget. Authorization admits one Clerk subject and issuer, so tables omit owner columns. Public errors carry fixed codes rather than raw causes, requests, or bank responses. Convex mutations need a thrown `publicError` to roll back and send that typed error; other failures stay values. Browser code and Convex share a pure domain module, enforced by lint import and global restrictions. Tests and orchestration retain throws and cleanup.

Bank sync applies three pages of 100 rows per mutation. Each row needs roughly a dozen reads for import identity, Payee and rename memory, monthly totals, nearby Transactions, and search text; 300 rows leave room under Convex's 4,096-document read budget. Three calls at the 35-second Plaid limit fit within the two-minute lease. A sync stops after four batches at a committed cursor to bound action duration. Search-text rewrites also batch, because each Transaction can read a Payee, up to 50 split lines, and Bank Rows. These are capacity choices, not additional sources of truth.

Input amounts are capped at $10 billion in either direction so sums of household amounts stay safe integer cents. A By date Target can repeat at most every ten years, beyond the intended bill horizon. File imports reject unusually large files; they decode in the browser and send only Bank Rows to the server.

CSV downloads are spaced by 200 ms because Chromium drops downloads beyond ten started together. The E2E export checks that every table arrives. The Blob URL is revoked after the synchronous download click returns.

The Convex URL is a build-time setting: `convex deploy` supplies the target URL to its build. Clerk's Convex integration supplies audience `convex`; the token callback stays stable within a session so routine Clerk updates do not re-authenticate Convex. A callback for an old session returns no token. Setup runs once within ClerkProvider during component setup.

Offline code generation uses Convex 1.48.0's internal system-UDF path because normal generation contacts a deployment for component analysis. This app has no components. That path omits typed environment declarations, so the script renders them with the same pinned CLI template and rejects version drift and mounted components. It excludes deployment-selection variables and env files.

Unmodified generated shadcn files are excluded from ESLint; project-owned customizations are checked by both ESLint configurations. The owned files are button/button.svelte, dialog/dialog-content.svelte, progress/progress.svelte, table/table-cell.svelte, table/table-head.svelte, table/table-row.svelte, and table/table-variants.ts under src/lib/components/ui/. The shared ignore list lives in eslint/ui-ownership.js. Svelte typechecks the entire directory. Column alignment uses typed variants in place of the obsolete HTML align attribute; TableHead and TableCell share those variants. The screen-sm variant uses the 640px viewport breakpoint, while the other showFrom variants use container queries. Strong rows mark Unapproved Transactions, wrapping buttons fit amount labels, and wide dialogs fit import tables and scroll when taller than the screen. Progress keeps root props typed separately because Svelte cannot represent the complete union through a spread. Domain tests use America/Los_Angeles so accidental UTC date shifts show up as the previous date. Vitest's inline projects do not inherit the app's SvelteKit plugins. SSR suites start real servers and need longer timeouts.

Playwright tests run serially because they share one seeded budget. Reconciliation uses the seeded Card, which later tests leave alone. Other mutating tests restore their edits. The local runner's isolation and credential rules live in `docs/agents/authentication.md`; it strips inherited deployment variables, refuses a busy preview port, and redacts Clerk refresh session IDs and browser tokens. A fresh backend initially rejects a push until issuer and owner are configured through stdin. On exit the runner restores caller SvelteKit types because SSR checks can leave incomplete public-env declarations.

Plaid webhooks are verified against Plaid's signing keys, kept for a day after each lookup so a webhook rarely costs a Plaid call. A key not kept is looked up at most once a minute for each Item, so forged tokens naming made-up keys cannot each cost a call, and a flood naming one Item cannot hold up webhooks for another. A webhook reaches the lookup only for an Item with a stored token, so lookups across the deployment stay bounded by the owner's few Bank Connections. A webhook whose key waits on its Item's limit, or that Plaid cannot serve because of an outage, rate limit, or timeout, is answered 429 with `Retry-After`, because Plaid retries only non-2xx responses other than permanent 4xx failures, for up to a day; the daily sync covers any webhook Plaid gives up on. Each lookup clears more expired key rows than it adds, so forged keys cannot grow the table. A key lookup makes one five-second attempt, because Plaid expects an answer within ten seconds and sends a webhook answered 429 again. A sync asked for while another holds the lease is recorded on the Bank Connection, and the holder schedules one more sync when it releases the lease, so a webhook during a sync is never lost. Webhook tokens older or newer than five minutes are refused as replays.
