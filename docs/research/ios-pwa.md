# iOS Home Screen PWAs for Budge

Researched **2026-10-27**. Scope: a single-user, YNAB-style budgeting app using SvelteKit, Convex, Clerk, and Vercel; iPhone installation through Safari; v1 requires a network connection. This is documentation research, not an implementation or an iPhone test. Recommendations below are conclusions for Budge, distinguished from documented platform behavior.

## Summary

- **An installed web app is a viable iPhone client without a Mac, Xcode, or an Apple Developer membership.** Safari supports Home Screen installation; even Web Push does not require membership. Since iOS 26, users can open any added website as a web app, without a manifest or service worker. Still provide a manifest and icons for Budge. [Safari 26](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [Apple push documentation](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)
- **Installation, offline support, and push are separate choices.** For online-only v1, start with a manifest and assets; add a small SvelteKit service worker only for a deliberate asset-cache or push requirement. Do not install a broad offline caching recipe. [SvelteKit service workers](https://svelte.dev/docs/kit/service-workers)
- **Installed storage has substantial capacity, but is disposable.** Home Screen apps receive browser-level quotas and an exemption from ITP's first-party seven-day deletion rule. Neither makes local storage the authoritative copy of a budget. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [Tracking Prevention](https://webkit.org/tracking-prevention/)
- **Treat the installed app as its own authentication context.** Since iOS 17.2, installation copies cookies, but subsequent website data is isolated from Safari. Clerk session continuity needs production-domain testing, including token refresh after a background interval. [Safari 17.2](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/), [Clerk architecture](https://clerk.com/docs/guides/how-clerk-works/overview)
- **Cache public build assets only; keep Convex and Clerk on the network.** A service worker cannot intercept Convex's WebSocket frames. It must not provide stale budget responses, replay mutations, or cache authentication responses. This is the recommended policy, based on the [WebSocket handshake specification](https://websockets.spec.whatwg.org/#opening-handshake) and the SDK behavior discussed below.

## Installation, display, manifest, and branding

The current iPhone flow is **Safari → Page Menu → Share** (or the visible Share button, depending on toolbar layout) **→ Add to Home Screen → leave Open as Web App enabled → Add**. Add to Home Screen can be enabled through Edit Actions if missing. Give the owner brief instructions inside Budge. Safari does not implement `beforeinstallprompt`, so an app button cannot invoke the Chromium installation dialog. [Apple iPhone guide](https://support.apple.com/guide/iphone/bookmark-a-website-iph42ab2f3a7/ios), [MDN event compatibility data](https://github.com/mdn/browser-compat-data/blob/main/api/Window.json)

Since **iOS/iPadOS 26**, web-app mode is the installation default; users can turn it off even when the site requests standalone display. On older releases, `display: standalone` or `fullscreen` in the manifest, or the legacy Apple capable meta tag, distinguishes an app from a bookmark. An installed app has its own App Switcher presence and no ordinary Safari address/toolbar UI. “Fullscreen” manifest display should not be interpreted as a promise to hide all system status UI. [Safari 26](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [WebKit Home Screen overview](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple standalone documentation](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html)

Recommended manifest fields: stable `id`, `name`, `short_name`, `start_url`, `scope`, `display: standalone`, `theme_color`, `background_color`, and icons. Use a stable production origin and an in-scope start URL without tokens or transient query parameters. Manifest support is member-specific; do not assume Android's complete feature set. The `id` member has been supported since 16.4; iOS combines identity with the user-chosen name for features such as Focus, and permits multiple installations. Detect the running context with the `display-mode` media query, with `navigator.standalone` as an Apple fallback. [WebKit identity](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [MDN display-mode](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/display-mode), [Apple standalone property](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariHTMLRef/Articles/MetaTags.html)

**Icons:** supply manifest PNG icons at 192 and 512 pixels for interoperability, plus an explicit 180×180 `apple-touch-icon` PNG for iPhone. iOS has supported manifest icons since 15.4, but `apple-touch-icon` takes precedence; manifest icons need omitted `purpose` or `purpose: any`. Do not supply only a maskable icon. The dimensions above are Budge's recommended asset set; Apple's reference documents the 180-pixel touch icon. [Safari 15.4](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/), [Apple icon reference](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html)

**Splash screens:** Apple documents `apple-touch-startup-image`; this is separate from manifest icons. A custom launch image may require device/orientation-specific assets and media queries, so do not assume `background_color` and a manifest icon reproduce Android's generated splash. For v1, prioritize a fast, matching first paint; treat custom splash behavior as an iPhone acceptance test. Apple's launch-screen reference is archived, so its historical default screenshot behavior is not a guarantee for every current release. [Apple launch screens](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html)

**Status bar:** the Apple-specific `apple-mobile-web-app-status-bar-style` supports `default`, `black`, and `black-translucent` in the documented standalone configuration. Translucency places content underneath the bar and requires safe-area handling. This is not an arbitrary status-bar color API; test light/dark mode and actual device rendering. Keep the legacy `apple-mobile-web-app-capable=yes` tag if supporting older iOS behavior. [Apple meta tags](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariHTMLRef/Articles/MetaTags.html)

## Push: useful reminders, no delivery guarantee

Conventional Web Push is available to **Home Screen web apps on iOS/iPadOS 16.4+**, not ordinary Safari tabs. Request permission directly from a deliberate user gesture in the installed app. Use HTTPS, a push subscription with `userVisibleOnly: true`, a service-worker push handler, and a server sender using VAPID and encrypted standard Web Push payloads. Apple Developer membership and an APNs native-app certificate are unnecessary. Notifications integrate with system settings and Focus; badging is supported. [WebKit introduction](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple sender requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)

Every conventional push must promptly display a notification, including when the app is open. Silent background refresh is unsupported; failing to show a notification risks revocation. Build the notification from the payload rather than waiting for a Clerk token or a budget query. Delivery depends on permission, device/network availability, TTL, and system notification settings. Apple documents limited offline queueing and expired-message removal; a successful send is not proof that the owner saw it. Handle expired subscriptions and reconcile subscriptions on foreground use. For Budge, reminders are optional conveniences, never the only record of a financial event. [Apple push delivery and errors](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)

**Newer option: Declarative Web Push, shipped on iOS/iPadOS 18.4.** It carries a standardized JSON notification and navigation target. `window.pushManager` can subscribe without an installed service worker; an optional worker can customize delivery, with the declarative notification as fallback if JavaScript fails or the worker disappears. A conventional handler can read that same payload for older browsers. Feature-detect the API; this improves resilience, not delivery certainty or permission eligibility. It does not enable silent push. Prefer this payload format if Budge later adds reminders, while retaining a conventional worker path where needed. [WebKit Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)

## Storage quotas, persistence, and eviction

Since Safari/iOS 17, an installed standalone app receives the browser-app policy: **up to 60% of total disk per origin and up to 80% overall across origins in its storage container**. These are upper limits, not reserved free space. They cover storage APIs including IndexedDB, Cache Storage, service-worker data, and file-system storage; cookies and HTTP cache have separate policies. `navigator.storage.estimate()` provides estimates. Catch `QuotaExceededError`. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)

Best-effort data can be evicted under device storage pressure or overall quota pressure. WebKit normally removes an origin's data together, using least-recent use; active origins or persistent storage can receive protection. Check `persisted()` and request `persist()`, then inspect its Boolean result: Home Screen use is a grant heuristic, not an automatic contract. Installation alone is not proof that persistence was granted. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)

The often-repeated “all iOS PWAs lose storage after seven days” is incorrect. WebKit explicitly exempts a Home Screen app's **first-party domain** from ITP's seven-day cap on script-writable storage, and isolates its data from Safari's ITP classification. This is distinct from quota eviction, user deletion, cookie expiry, or application session expiry. [WebKit Tracking Prevention](https://webkit.org/tracking-prevention/)

Web Storage remains small—MDN documents roughly 5 MiB each for localStorage and sessionStorage—despite the larger origin quota for other APIs. Budge should keep the authoritative budget in Convex, keep any local state reconstructible, and recover from a missing cache or worker on the next online launch. Persistent mode cannot protect against the user's explicit deletion. [MDN quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## Service-worker lifecycle and background limits

Service workers are supported on iOS since 11.3. They are event-driven workers, not continuously running background applications: WebKit starts them when needed and terminates them when idle/no longer needed. Use `event.waitUntil()` for bounded event work; do not depend on global variables, timers, or a worker-owned WebSocket surviving app backgrounding. The 2018 WebKit introduction is useful for lifecycle principles, but its old fixed 50 MiB cache limit has been superseded by the storage policy above. [WebKit implementation](https://webkit.org/blog/8090/workers-at-your-service/), [MDN service workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)

Registration requires a secure context (HTTPS in production). A replacement worker generally waits while the previous version controls open clients; `skipWaiting()` and `clients.claim()` change that coordination. Do not force-reload an owner entering a transaction. Check for updates during suitable foreground use and offer a refresh after edits finish. Safari 27, released September 2026, adds static service-worker routing; this is optional optimization, not a reason to require the newest OS. [MDN lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers), [Safari 27 release](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)

Safari does not support the standard one-off Background Sync or Periodic Background Sync APIs according to current MDN compatibility data. A worker cannot make v1 into a reliable offline mutation queue or a scheduled background budget synchronizer. Do scheduled reminders/server jobs on the backend and recover connections on foreground return. [MDN SyncManager data](https://github.com/mdn/browser-compat-data/blob/main/api/SyncManager.json), [MDN PeriodicSyncManager data](https://github.com/mdn/browser-compat-data/blob/main/api/PeriodicSyncManager.json)

## Safe areas, viewport, and the software keyboard

Use `width=device-width, initial-scale=1, viewport-fit=cover` if drawing edge to edge, then protect controls with `env(safe-area-inset-top/right/bottom/left)`. Insets supplement ordinary padding, for example `padding-bottom: max(1rem, env(safe-area-inset-bottom))`. Cover is an opt-in responsibility: test portrait, landscape, notches/Dynamic Island, and the home indicator. [WebKit safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)

Prefer natural document scrolling. For a full-height layout, use modern `svh`/`dvh` as appropriate: `svh` favors a stable safe height and `dvh` follows browser chrome changes; plain `100vh` can hide controls behind expanded browser UI. **`100dvh` alone is not a keyboard strategy.** The keyboard can shrink the visual viewport without shrinking the layout viewport. Use `window.visualViewport` resize/scroll measurements when a fixed editor/footer needs them; keep focused fields and Save reachable, without disabling pinch zoom. [MDN viewport units](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length), [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)

Known reported quirks include bottom safe-area padding remaining when the keyboard appears ([WebKit bug 217754](https://bugs.webkit.org/show_bug.cgi?id=217754)) and viewport displacement around Dynamic Island/keyboard dismissal on iOS 26 ([bug 300523](https://bugs.webkit.org/show_bug.cgi?id=300523)). Both tracker pages were marked NEW when consulted; that is a report status, not confirmation that every current iPhone reproduces them. Avoid hard-coded keyboard heights or universal workarounds based on an old OS report; test the owner's exact device and iOS version.

## Clerk sessions in standalone mode

On iOS 17.2+, creating a Home Screen app copies cookies from the originating browsing context. Other local storage is not copied; after installation, website data is not continuously shared. Therefore signing in later in Safari does not itself populate the installed app's cookies, and changing a Safari cookie is not a standalone logout mechanism. Server-side session revocation is a separate matter. Older versions need their own sign-in flow. [WebKit Safari 17.2](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/)

Clerk uses a long-lived, HttpOnly `__client` cookie on its Frontend API domain to obtain short-lived session tokens; the app-domain `__session` token expires after about 60 seconds and the SDK refreshes it. In production the FAPI is a same-site subdomain such as `clerk.example.com`; development uses a different cross-site architecture. A copied app cookie is not proof of durable authentication: the FAPI credential and successful refresh matter too. [Clerk architecture](https://clerk.com/docs/guides/how-clerk-works/overview), [Clerk environment differences](https://clerk.com/docs/guides/development/managing-environments)

**Recommendation:** use Clerk's production instance/domain setup and supported SDK session management; sign in within the installed app when necessary. Do not invent token persistence in localStorage or a service-worker cache. Check cold launch and foreground return after token expiry, and wait for Clerk and Convex authentication readiness before enabling writes. Apple's cookie-copy announcement does not specify enough about every Clerk subdomain/OAuth configuration to promise seamless install-time login. OAuth redirects, popups, and email-link callbacks must be tested for return to the intended standalone context; a Safari callback cannot be assumed to transfer a new login automatically. These are integration acceptance criteria, not a claim that Clerk is universally broken on iOS.

## European Union behavior

The proposed removal of Home Screen web apps during the iOS 17.4 beta was reversed before general release. The European Commission records Apple's **1 March 2024** confirmation that the capability would continue in the EU. Budge does not need an EU-specific “PWA unavailable” fallback based on those beta-era articles. [Commission's primary-source Q&A](https://digital-markets-act.ec.europa.eu/citizens-and-whistleblower-portal/eu-citizens-qa_en)

EU alternative-engine browser entitlements and native-app Web Distribution are separate from installing Budge through Safari. Apple also exposes APIs allowing alternative-engine browsers to supply a web app's manifest and cookies to the system; that does not establish that Safari-installed Home Screen apps use another engine. Keep Safari/WebKit as this research's target, and test other installation paths separately if supported later. [Apple browser integration API](https://developer.apple.com/documentation/safariservices/sfaddtohomescreenactivityitem), [Apple EU platform changes](https://developer.apple.com/support/apps-in-the-eu)

## SvelteKit tooling recommendation

**For Budge v1: manifest and icons first; use SvelteKit's built-in worker if a worker is needed.** A small explicit policy is easier to audit for an online-only financial app. SvelteKit bundles and auto-registers `src/service-worker` entries; it does not require a PWA plugin. Current Kit docs use `src/service-worker/index.ts` (also `.ts`/`.js` at the root), `$app/service-worker`, `$app/manifest`, and `$app/env`. Kit 2 examples instead use `$service-worker` exports such as `build`, `files`, and `version`; follow the installed major's docs. Do not copy the documentation's general-purpose runtime GET cache into Budge. [Current SvelteKit guide](https://svelte.dev/docs/kit/service-workers), [Kit 2 legacy module](https://svelte.dev/docs/kit/$service-worker)

**`@vite-pwa/sveltekit` remains a useful integration when Workbox is justified**, providing manifest generation, precaching, registration/update helpers, and `generateSW` or custom `injectManifest`. It is not a prerequisite for iOS installation. As checked on the research date, npm's latest package is **1.1.0**, whose peer range is `@sveltejs/kit: ^1.3.1 || ^2.0.1`; current SvelteKit documentation includes Kit 3 APIs. Do not infer Kit 3 compatibility from “SvelteKit” in the package name. Resolve and pin compatible versions before choosing it. [Published package metadata](https://registry.npmjs.org/@vite-pwa%2fsveltekit/1.1.0), [Maintainer package source](https://github.com/vite-pwa/sveltekit/blob/main/package.json), [Integration docs](https://vite-pwa-org.netlify.app/frameworks/sveltekit.html)

For a compatible Kit version, use `generateSW` for a simple audited asset-only configuration; choose `injectManifest` when custom push handlers or routing require worker code. If plugin virtual registration owns registration, disable Kit's automatic registration with `kit.serviceWorker.register: false`. Restrict precache globs to public client files: plugin defaults include prerendered HTML/JSON. Its source defaults `navigateFallback` to the adapter fallback/base, so explicitly disable that for Budge's network-only navigations (`null` for the Workbox option). Do not let an SPA fallback swallow auth callbacks or server routes. [Integration docs](https://vite-pwa-org.netlify.app/frameworks/sveltekit.html), [Plugin configuration source](https://github.com/vite-pwa/sveltekit/blob/main/src/config.ts), [Workbox option definition](https://github.com/GoogleChrome/workbox/blob/v7/packages/workbox-build/src/types.ts)

Use a prompt-based update experience if caching is enabled; Vite PWA explicitly recommends it for apps with forms. Defer activation/reload until unsaved transaction edits and pending saves are handled. [Vite PWA update guidance](https://vite-pwa-org.netlify.app/guide/auto-update.html)

## Coexistence with Convex and Clerk: proposed cache contract

The browser's WebSocket opening handshake explicitly uses service-worker mode `none` and cache mode `no-store`: a fetch handler cannot intercept/cache Convex WebSocket frames. Keep the Convex client in the page and let its SDK own subscriptions, authentication, and reconnection. The shared client implementation reconnects; the browser client provides `setAuth(fetchToken)` with expiry refresh and connection-state observation. Do not put another Convex client inside the worker. [WebSocket specification](https://websockets.spec.whatwg.org/#opening-handshake), [Convex connection implementation](https://github.com/get-convex/convex-js/blob/main/src/browser/sync/web_socket_manager.ts), [Convex browser client](https://docs.convex.dev/api/classes/browser.ConvexClient)

The following is a **Budge recommendation**, not a browser-enforced default:

| Resource | Service-worker policy |
| --- | --- |
| Exact allowlisted, same-origin, content-hashed JS/CSS and public fonts/images | Optional precache/cache-first, bounded and versioned; successful public GET responses only. |
| Manifest, icons, optional generic offline explanation | Public assets only; revalidate/version deliberately. An explanation must contain no cached budget data. |
| HTML navigations and SvelteKit route/load data, including `__data.json` | Network-only. Never persist personalized SSR, route data, redirects, or signed-in pages. |
| Convex HTTP queries/actions, uploads/downloads containing private data, and any same-origin API proxy | Network-only; no runtime caching and no worker retry queue. WebSocket traffic already bypasses the worker. |
| Clerk Frontend API, session/token refresh, sign-in/out, OAuth callbacks, verification/email links | Network-only; preserve normal credentials and redirects. Do not precache Clerk SDK/API hosts broadly. |
| Non-GET requests, token-bearing URLs, requests with Authorization, arbitrary cross-origin requests | Bypass the cache. An asset allowlist must still be required for credentialed same-origin GETs, which can carry cookies. |
| Service-worker script | Fetch/revalidate for updates; never serve it indefinitely from its own asset cache. |

Enforce this with a small positive allowlist: everything else falls through to the network without `respondWith`, or uses an explicit network-only handler. Apply `Cache-Control: private, no-store` to personalized server responses as appropriate for browser/CDN caching, **and** exclude them in worker code. The Cache API does not honor HTTP cache headers automatically; `no-store` alone cannot prevent an overly broad `cache.put()`. Delete only Budge-owned old cache names. [MDN Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache)

On app resume, allow Clerk to refresh and Convex to reconnect before presenting a write as saved. Use actual connection/auth readiness rather than `navigator.onLine` alone. Handle pending writes in the page; an SDK retry during a live page session is not a durable queue after iOS kills the process. Do not replay financial mutations from Workbox Background Sync or show an offline-ready budget claim merely because assets were cached. [Convex client and auth lifecycle](https://docs.convex.dev/api/classes/browser.ConvexClient), [Convex transport implementation](https://github.com/get-convex/convex-js/blob/main/src/browser/sync/web_socket_manager.ts)

## Acceptance checks and remaining uncertainty

Before calling the iPhone experience supported, check on the owner's physical iPhone over production HTTPS:

1. Fresh Home Screen install, correct icon/name, standalone launch and deep-link navigation; repeat with Open as Web App disabled to verify instructions.
2. Standalone sign-in, close/reopen, device lock, long background interval, expired token refresh, sign-out, OAuth/email callback, and reinstall. Exercise the production Clerk domain, not just a Vercel preview with development credentials.
3. Wi-Fi/cellular transitions and airplane mode during a save; truthful reconnect/pending/error states and server-confirmed results after resume.
4. Amount-entry keyboard, Save, bottom navigation, rotation, zoom, light/dark appearance, and device safe areas.
5. A deployment while a transaction form is dirty, plus deleted caches/storage. If push is added, test both foreground and closed-app receipt, Focus, revoked permission, expired subscription, and notification-tap routing.

No physical-device results are claimed here. In particular, exact current splash rendering, cookie transfer across Clerk's relevant origins, and callback return behavior remain integration tests. A Mac is not required to install or use Budge; Apple's usual remote Web Inspector workflow uses Safari on macOS, so the no-Mac constraint limits that debugging route. Use visible connection/error diagnostics and sanitized server logs during iPhone acceptance testing. [WebKit inspection documentation](https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/)
